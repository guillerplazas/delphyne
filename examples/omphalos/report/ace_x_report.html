Omphalos ACE Study

Backup material for the advisor meeting: the new benchmark partitions, the platform work that made the larger runs affordable, how ACE (Agentic Context Engineering, arXiv:2510.04618) was rebuilt on Delphyne, the paper's experiments replicated in our setting, and what it bought. Every number is regenerated from recorded runs (, rates of ).

1 · Benchmark: the X partitions

  • Why. The original 20-problem partitions saturated for the cheap pipelines: train 20/20, test 16/20 with the same sixteen for every luna-class arm, validation with zero discordant cells anywhere — nothing left to rank.
  • What. Three new partitions of 40 problems each (trainX tune · validationX select, two seeds · testX one look per headline arm), drawn from miniF2F valid+test minus the old partitions, the ACE adaptation pool and the demos; a family quota puts 50 % competition problems (IMO/AIME/AMC) in each, against 15–35 % before. Generated and checked by tools/make_partitions.py --check; reserved for luna-class pipelines.
  • Result. The canonical baseline drops to 27/40 on both validationX seeds (12 problems never solved) and 32/40 on testX — real headroom, at ~$0.02 per cell.

2 · Performance: making 80-cell runs routine

  • The problem. Doubling the partitions doubled every run; overnight runs were single-worker, hung on runaway tactics, and died to memory balloons and orphaned processes.
  • What was measured before changing anything. Every Rocq tool call rebuilt the document from scratch; the "warm server" of the previous night wrote a random temp file per call and leaked ~50 MB per call; the worker balloons were unbounded Rocq replies, not the search tree; the wall-clock tail was goal floods (up to 1128 open goals probed by the battery).
  • What changed. A private warm Rocq server per process on stable document paths, deadlines and reply caps on every RPC, memory bounds and recycling, a prefix-state memo; a launch layer with a lock per directory, a FIFO queue of four machine-wide Rocq streams, supervised attempts that rebuild statuses from disk, and make stop for the videocall case.

3 · ACE implementation on Delphyne

  • Generator = the canonical prover (prove_theorem_agentic: 32-turn agentic loop, verifier feedback every turn, Rocq tools) plus one system-prompt section, the playbook. Same strategy, same policy, same caps; archived prompts replay byte-identically.
  • Reflector and Curator are one-shot Delphyne strategies with their own request/dollar caps. No ground truth exists: the Rocq verdict inside the trajectory is the supervision (the paper's "no GT labels" setting).
  • Curator proposes ADD-only deltas (as the reference implementation does); merging, dedup, counters, the size guard and pruning are deterministic code — the LLM never rewrites the playbook (the monolithic arm is the ablation that lets it).
  • Playbook: bullets with stable ids, sections tactics / lemmas / pitfalls / strategy, helpful/harmful counters; content-addressed store (by_hash/<sha256>.yaml) so every cell pins the exact playbook it saw; frozen playbooks carry a provenance sidecar.
  • Offline: adapt on trainX (batches of 4 through the reference's aggregation prompt), freeze, evaluate on validationX (two seeds) and once on testX. Online: predict-then-update per problem along validationX.
  • v4 adds the reference's attribution channel: the Generator names the bullet ids it relies on, the Reflector sees only those, counters move only for them.

The generator strategy — the prover with one extra section

@strategy
def prove_theorem_ace(problem_file, theorem_name, toolset="core", turn_budget=32,
                      playbook="", show_definitions=False, render_version=1, ...):
    spec = pt.parse_problem(problem_file, show_definitions)
    script = yield from dp.interact(
        step=lambda prefix, _: ProposeProofScriptACE(       # system prompt = canonical + playbook section
            spec, available, toolset, turn_budget, prefix, playbook, render_version
        ).using(dp.ambient_pp),
        process=lambda s, _: check_proof_assisted(problem_file, theorem_name, s)   # Rocq verifier
            .using(dp.just_compute),
        tools={ReadSkill: ..., SearchRocq: ..., InspectAt: ..., TryAutomation: ..., TryTactics: ...},
    )
    return script

One adaptation step, as the driver runs it

for batch in plan(variant):                     # trainX order, seeded shuffle, batches of 4
    sha = store.put(pb)                         # every member sees the batch-start playbook
    gen  = run("generator", batch, sha)         # prover cells, Rocq slots
    refl = run("reflector", gen)                # LLM-only: trajectory + outcome (+ cited bullets in v4)
    cur  = run("curator", refl)                 # LLM-only: ADD-only delta, ≤ 3 bullets
    delta = reduce(cur)                         # LLM-only: one aggregation over the batch's deltas
    pb = merge(pb, delta.operations, tags, deduper, max_tokens=4000).playbook
    if step % refine_every == 0: pb = refine(pb, deduper, prune_harmful=True).playbook

Mapping to the paper's experiments

Design decisions, sacrifices and adaptations

  • No ground-truth labels anywhere (no proof exists to compare to): the paper's "GT ✗" column for every arm; the verifier's verdict is the only supervision.
  • One reflection per sample, no reflect→regenerate repair loop (paper: up to 5 rounds): our Generator already gets verifier feedback on every one of its 32 turns — the domain-native repair loop. A faithful repair round would cost a full extra prover cell per round.
  • Hard 4k-token size guard (8k on the multi-epoch arm) instead of an advisory 80k budget: every playbook token is resent on every turn under a per-problem dollar cap.
  • Counters hidden from the Generator (v2+) for prompt-cache stability; shown to the Reflector and Curator.
  • Batches of 4 with the reference's aggregation prompt on the v3/v4 offline arms (paper: batch size 1); a 12-step gate showed equal solves and a 2.5× smaller playbook.
  • Same model in all three roles (gpt-5.6-luna, as the paper does), each under its own request/dollar cap.
  • Online = window of 1 (paper: windows of 15): predict on the problem, then update.
  • No best-playbook checkpoint (final playbook frozen; every step's playbook is stored).
  • Dedup is inert here (0 folds in every variant; the reference's is off by default).
  • Not run, disclosed: reflection repair rounds, v3 warm-start chains (v2 answered warm-up negatively), top-k injection on v3.

    7 · Q&A

    Why did the v3 numbers change between the two versions of this report?

    The first "v3" evaluations were run by a script that consumed --playbook= on its first read and fell back to the v2 file, and rendered every playbook at prompt version 2. Every v3 arm was re-evaluated correctly on 2026-08-26/27; the mis-run cells are kept and reported as replicates of the v2 arm — a paid measurement of the run-to-run noise floor.

    Is 57 vs 54 with 3–0 discordant cells a result?

    It is the first offline arm that wins cells without losing any, on both seeds; but three discordant cells are below the six-cell power floor (p=0.25 two-sided), identical configurations disagree on 2–3 cells run to run, and the same playbook is 32 vs 32 on testX. It is a direction, not a finding.

    Why does ACE not transfer here when it gives double digits on AppWorld and FiNER?

    Those tasks lack per-step feedback; the playbook supplies the missing environment knowledge. Our Generator already gets the Rocq verifier's exact verdict and remaining goals after every proposal, plus tools to search the library — the playbook adds general advice on top of specific feedback. The paper itself says ACE is most useful where detailed domain knowledge or environment-specific strategies are missing.

    Does the no-Reflector arm scoring the same as the full arm mean the Reflector is useless?

    On this benchmark the Curator fed the raw trajectory produces a playbook of the same size and effect (57 vs 54 both). The Reflector's diagnosis is not what moves solves here; it does move counters, which move nothing measurable.

    What about the reference's attribution channel (v4)?

    Implemented as the reference does it (Reflector sees only cited bullets, counters only for them), run as a minimal pair of the v3 offline arm: 55 vs 57 (2–4). It changes the counters, not the solves.

    Multi-epoch made things worse — why?

    Three epochs at an 8k guard grew the playbook from 26 to 54 bullets (4.5k tokens); the evaluation lost four cells against the single-epoch playbook (53 vs 57). More context is more to read on every turn, and the added bullets are increasingly theorem-specific.

    Did context collapse reproduce?

    Partly. The monolithic-rewrite arm shows one-step drops of ~600 tokens and the Curator failed 52 % of its rewrites (unparseable output), yet it scored 55 vs 54 — the paper's −13.4 does not appear. Deterministic merging keeps the incremental arms from ever shrinking.

    Is the study memorising the benchmark?

    Adaptation runs on trainX; validationX selects; testX is looked at once per headline arm and no testX failure was used to change anything. The playbooks name lemmas and tactic patterns, not theorems.

    What did the whole ACE study cost?

    About $16 for the corrected matrix (nine 80-cell evaluations and chains at $1.5–2 each, adaptations at $1–3), on top of the earlier generations; the platform cost of one 80-cell evaluation is now ~45 minutes at four workers.

    Can the experiments be paused for a call?

    Yes: make stop frees the memory within a minute (in-flight cells are re-paid on resume); make -j3 ace-x-matrix re-queues everything and skips what is done.

    What would you do next?

    Nothing more on offline playbooks at this model class: the effect is bounded by the noise floor. The open levers are the reference's repair rounds (a full prover cell per round) and, more promising for the thesis's control theme, using the Reflector's diagnosis to route budget rather than to write prose — the two-tier policies already pre-registered.

    Why was ACE null on the original partitions, and why should the X partitions change that?

    Because those partitions could not rank luna-class arms any more: train was 20/20 for every toolset, test was 16/20 with the same sixteen problems for terra, luna and ACE, and a paired test needs six discordant cells for significance while identical configurations already disagree on one to three. The X partitions are twice as large and half competition problems, so the baseline has headroom to lose or gain.

    Is the playbook just memorising trainX lemmas?

    Partly by design — the paper's playbooks are explicitly domain-specific — but validationX and testX are disjoint from trainX and from the demo problems, and the bullets are inspected in the adaptation logs: lemma bullets name stdlib lemmas, not problem-specific facts. The online arms answer the question from the other side: they learn on the partition they are evaluated on, which is the paper's test-time setting, and their cells are only ever compared with the baseline cell of the same problem.

    Where is the ground truth? The paper has a "with labels" arm.

    The Rocq checker is the label: a verified proof is correct, a rejected script is wrong, no exceptions. That collapses the paper's GT axis — every omphalos arm is the "execution feedback, no labels" setting, which is also the paper's strongest realistic claim.

    Why hide the helpful/harmful counters from the Generator?

    Three reasons: the Generator cannot use them (it has no attribution channel back), rendering them makes every counter change invalidate the prompt cache on every step, and most counters are zero early on, which reads as "unvalidated advice". Counters still gate refinement and are shown to the Reflector and Curator, who do attribute.

    Why were the definitions hidden until now, and does fixing that confound the comparison?

    A parser gap: the prompt builder captured only imports, so 42 of 488 files asked for a proof about a symbol the model never saw. It was measured once in isolation (+1 of 8 affected cells) and is on for every X-partition arm, baseline included, so it is a constant, not a variable.

    Offline vs online: which is the fair comparison?

    Offline is the paper's headline and the clean one — frozen playbook, unseen partition. Online adapts on the evaluated partition, so its cells are compared only with the baseline's cells for the same problems, in the same order; the warm-up variant is the paper's best configuration. Online arms were developed on validationX; only the variant selected there gets a testX look.

    What would a stronger Reflector change?

    The paper's Table 16 shows Reflector quality moves the result more than Generator quality. Omphalos pays for adaptation once and for generation on every problem, so a terra Reflector on a luna Generator is the cheap place to spend — the driver already exposes it (reflector_model), pre-registered as HINTS #49.

    How do you know the refactor did not change what was measured before?

    The frozen 2026-08-24 adaptation chain was re-derived from its caches through the new driver at zero spend and ended in the same playbook hash (30ffc40f); all four smoke commands replay with zero cache misses under cache_mode: replay.

    Cached tokens are cheap — is the playbook really free per turn?

    No: cached input is 10× cheaper than fresh input but not free, and a long playbook still costs on every turn. The evaluation-stage table reports billed spend and cached share per arm so the trade can be read directly rather than argued.
